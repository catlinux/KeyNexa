# Threat model

[English](THREAT_MODEL.md) | [Español](es/THREAT_MODEL.md)

> Status: **initial draft** (v0.1.0), written before any sensitive code. It will be revised at every phase. KeyNexa has not been audited; nothing here is a guarantee.

## Assets

| Asset | Where it lives |
| --- | --- |
| Decrypted vault contents (passwords, notes, attachments, TOTP secrets) | App memory while unlocked |
| Master password and key file | User's memory / user-chosen file; transiently in app memory |
| Derived keys (composite key, transformed key) | App memory while unlocked |
| Encrypted vault file (`.kdbx`) | User storage, synced folders, private backups |
| Biometric unlock material (master key wrapped by a Keystore key) | App-private storage + Android Keystore |
| Release signing key | Maintainer only, never in the repository or CI logs |

## Attackers in scope

1. Someone with physical access to a **locked** device (theft, loss).
2. Someone with brief access to an **unlocked** device.
3. A malicious app on the same device (no root): overlays, clipboard reading, fake autofill targets, a malicious keyboard.
4. Someone who obtains the encrypted `.kdbx` file (from a synced device, a backup, a cloud copy) and attacks it offline.
5. A compromised or malicious sync peer that modifies or corrupts the file.
6. A compromised dependency or build pipeline (supply chain).

**Out of scope:** a rooted or compromised operating system, hardware attacks on the Keystore/TEE, a user who reveals their master password, and malware with accessibility-service control of the device. These are documented as residual risks.

## Threats and mitigations

| # | Threat | Mitigation (planned unless stated) |
| --- | --- | --- |
| T1 | Offline brute force of the master password | KDBX 4 with Argon2id as default for new vaults, parameters calibrated per device (target: about 1 s unlock) with sane minimums; password-strength feedback when creating a vault; key-file support. Existing vaults keep their own KDF settings unless the user changes them. |
| T2 | Weak or custom cryptography | No custom crypto. All primitives come from the KDBX engine (kotpass, ported from Bouncy Castle) and the platform (`javax.crypto`, Keystore). KDBX 4 header and block HMACs are always verified. |
| T3 | Secrets in memory | Keep decrypted data only while unlocked; protected fields decrypted on demand; prefer `ByteArray`/`CharArray` and zero them after use; drop references on lock. **Limitation:** on the JVM/ART, `String` objects and copies made by the garbage collector or UI toolkit cannot be reliably wiped. |
| T4 | Secrets in logs, crash reports, temp files | No logging of secrets (lint rule + review checklist); no third-party crash reporting; no temporary plaintext files; release builds strip debug logging. |
| T5 | Screen capture, recents thumbnail | **Implemented:** `FLAG_SECURE` is applied before `setContent` when “Allow screenshots” is off; that setting is off by default and can be enabled by the user. |
| T6 | Clipboard leakage | **Implemented:** sensitive clips are marked as such (Android 13+) and all carry a KeyNexa marker; auto-clear uses the configured timeout and clears only a clip with that marker. Android only lets the app clear the clipboard while it is in front, so a due clip is cleared when the user returns if another app is open. |
| T7 | Keyboard learning or keylogging | **Implemented with a limitation:** password fields use password input types and disable autocorrect. Compose does not expose `IME_FLAG_NO_PERSONALIZED_LEARNING`, so a third-party keyboard may still learn from or see typed passwords. Since 0.32.0 the master password is typed by default with the KeyNexa keypad ([ADR-0010](decisions/0010-in-app-password-keypad.md)), which keeps the system keyboard out of the path; the limitation remains when the user switches to the system keyboard. |
| T8 | Unattended unlocked app | **Implemented:** a `Handler` schedules the selected-timeout lock while the process is active. Deep sleep can delay the timer; elapsed time is checked on return, and screen-off locking also applies. Locking clears credentials and decrypted data. |
| T9 | Biometric unlock abuse | Master key wrapped by an Android Keystore AES key with `setUserAuthenticationRequired(true)`, per-use authentication through `BiometricPrompt` + `CryptoObject`, `BIOMETRIC_STRONG` only, invalidated when biometrics change; StrongBox when available. Opt-in, with a periodic master-password re-prompt. |
| T10 | Android backup exfiltration | `allowBackup="false"` plus explicit `dataExtractionRules` and `fullBackupContent` excluding all app data; secrets in `noBackupFilesDir`. |
| T11 | Malformed or malicious `.kdbx` | KDBX 4 header and block HMACs verified before parsing (KDBX 3.1 relies on its stream start bytes and hashed blocks); limits on sizes and KDF parameters to avoid memory exhaustion, and a conflict copy that asks for more than 16 times the open vault's key derivation work is not decrypted (0.33.5); XML external entities and DTDs refused on every platform, including XML key files (0.33.7; the audit found the parser did not do it before); fuzz tests on the engine adapter. |
| T12 | Data loss on save (interruption, truncation, partial writes) | Safe-save pipeline: private backup, `"rwt"` write, read-back verification, restore on failure ([ADR-0004](decisions/0004-storage-sync-and-safe-save.md)). |
| T13 | External changes and sync conflicts overwritten | **Implemented:** fingerprint checks run before saves and on resume; external vault changes are merged automatically by UUID and timestamps. Syncthing `.sync-conflict-` copies are merged when the vault opens. The app offers to delete successfully merged copies and deletes them only after consent and a matching fingerprint check. |
| T14 | Phishing through autofill (fake package names) | Credentials matched to apps by verified signing certificate and Digital Asset Links, not by package name alone; explicit confirmation when not verified. (Phase 2.) |
| T15 | Excessive permissions | **Implemented:** the `offline` build declares no `INTERNET` permission and never accesses the network; the `cloud` build declares `INTERNET` only to reach the service the user configures, and only the `offline` build is published until the cloud features are complete; no `MANAGE_EXTERNAL_STORAGE`; SAF only. |
| T16 | Supply chain | Few dependencies, pinned in a version catalog; Gradle dependency verification (checksums); automated vulnerability and license checks in CI; the release workflow pins every action to a commit (0.33.6); reproducible-build investigation before 1.0. |
| T17 | Signing key compromise | Key kept offline by the maintainer; CI signs only through encrypted repository secrets, in a job of its own that runs no Gradle and no third-party code (0.33.6); never committed. |
| T18 | Cloud account compromise (someone gets into the chosen service) | Only encrypted copies are uploaded, so the attacker gets ciphertext; a strong master password and an optional key file are the real protection. The copy count is limited and the consent text warns that old copies can hold old passwords. Only the `cloud` variant includes this code. |
| T19 | Theft of the local cloud credentials | Stored encrypted with a non-exportable AES-256-GCM key from the Android Keystore, in app-private storage excluded from Android backup; never logged and never shown; "Disconnect and delete" removes them. |
| T20 | Exposure of file metadata (name, size, times) | The service sees only the object name (the vault name sanitised to letters, digits, `-` and `_`, plus 8 characters of a hash of the file's location, which reveal nothing about it), its size and its times, never its content; the user can choose a vault name that does not identify it. |
| T21 | Interception of the connection | HTTPS only in production, with the system's TLS validation; redirects are not followed, so a signed request is never re-sent to another host; URLs, headers, keys and bodies are never logged. |
| T22 | Keylogger or malware on the device captures the master password or the revealed secrets | **Not preventable by the app** (a compromised OS is out of scope), so the design limits the damage: an optional key file kept apart from the vault means the typed password alone does not open a stolen `.kdbx`; biometric unlock and "copy sensitive" avoid typing and showing secrets; 2FA on important accounts keeps a stolen password from being enough. Done: touches are ignored while another app draws over KeyNexa, the create screen explains the optional key file and its risk, and the unlock screen quietly mentions a keyboard or accessibility service that does not come with the system. The master password is typed by default with the KeyNexa keypad (0.32.0), so a malicious keyboard does not see it; an accessibility service still could. With a screen reader on, the system keyboard is used, since the keypad would speak each key aloud. |
| T23 | Desktop: another program running as the same Windows user reads the process memory, the private data in `%LOCALAPPDATA%\KeyNexa` or the DPAPI-protected secrets | **Not preventable by the app** (DPAPI protects against other Windows users and against a copied disk, not against the same user), so it is accepted and documented, as T22. **Implemented** (desktop 1.5.0, [ADR-0012](decisions/0012-windows-desktop-client.md)): only encrypted vault bytes, fingerprints and non-secret settings are written there, never plaintext; the vault locks after inactivity in the KeyNexa window (5 minutes by default), on Windows session lock and on suspend (Windows session and power notifications, no polling), and the clipboard is cleared when it locks. |
| T24 | Desktop: screen capture, clipboard history and cloud clipboard | **Implemented** (desktop 1.5.0, [ADR-0012](decisions/0012-windows-desktop-client.md)): the window is excluded from capture with `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` unless the user allows screenshots (Windows 10 2004 and later; Microsoft states it is not a guarantee, and nothing stops a photo of the screen); copied passwords, protected fields, one-time codes and notes carry the formats that keep them out of the Windows clipboard history and cloud clipboard, and are cleared after the timeout, on lock and on exit, only if the clipboard still holds them. |
| T25 | A hostile device on the local network attacks device synchronisation (connects, impersonates a peer, sends malformed input) | Planned ([ADR-0013](decisions/0013-device-sync.md)): only devices with the synchronisation mode on listen (the "local only" desktop mode opens no socket); TLS 1.3 only with mutual authentication and certificates pinned at pairing; single-use pairing token valid for two minutes, confirmed on screen; opaque DNS-SD name; size and time limits, a delay after failed handshakes; message decoder fuzzed before release. It can still see that a KeyNexa device is listening and on which port. |
| T26 | A stolen device key or a compromised paired device sends a bad or rolled-back vault | Planned ([ADR-0013](decisions/0013-device-sync.md)): an incoming file is merged only after it decrypts with the open vault's credentials, otherwise it is kept as a pending copy and reported; a locked device never replaces its vault file; deletions travel only as KDBX deleted objects and history is kept; the private backups remain; removing a device revokes it. A paired device that knows the master password can change the vault like any client. |
| T27 | Someone with the cloud account deletes or rolls back the synchronised object ([ADR-0009](decisions/0009-cloud-sync.md)) | Done (1.6.7–1.8.5): the local file stays the source of truth, a rolled-back object is merged (never copied over the local vault), and the rotated copies of ADR-0008 and the private backups remain. |
| T28 | Desktop: someone at the unlocked Windows session, or a dump of the locked process, uses the quick unlock with Windows Hello | Done (1.10.0, [ADR-0014](decisions/0014-windows-hello-quick-unlock.md)): opt-in, off by default; only the pre-KDF key components are kept, **in memory only**, encrypted with AES-GCM under a key derived from a Windows Hello signature (the Hello key is not exportable and every signature asks for the PIN, face or fingerprint); expires after 1 to 24 h (8 by default) counted from the master-password unlock; wiped when the app closes, on another vault, on wrong credentials or a Hello error; the first unlock after starting the app always asks for the master password. Someone who knows the Windows PIN can open the vault within that time. |
| T29 | A malicious or tampered update reaches users through the update channel (stolen GitHub account, compromised workflow, hostile network, downgrade) | Done (1.12.0 on Windows, 1.14.0 on Android `cloud`; [ADR-0015](decisions/0015-automatic-updates.md)): opt-in; only newer versions are offered; on Windows a manifest signed with a KeyNexa Ed25519 update key, whose public half is built into the app, and the SHA-256 it lists are checked before `msiexec` starts; on Android the downloaded APK must carry the installed app's signing certificate, and the system checks it again; the user confirms every install; the `offline` build never checks. |

## Residual risks (accepted, documented to users)

- A rooted or malware-infected device can read memory and input.
- JVM strings and UI text fields may keep copies of secrets in memory until garbage collection.
- Third-party keyboards see typed passwords.
- Syncthing on Android is a third-party app; its behaviour (for example how it replaces files) can change, and recent Android security patches (September 2026) revoke file-level URI permissions when a synced file is replaced. KeyNexa mitigates this with folder grants and a "reconnect file" flow, but cannot control it.
- KDBX security depends on the strength of the master password.
- A keylogger or screen-reading malware on the device can capture the master password when it is typed; protect yourself with a key file stored apart from the vault and with 2FA on important accounts (T22).
- On Windows, any program running as the same user can read KeyNexa's memory and its DPAPI-protected secrets (T23).
- Device synchronisation works only on the same local network or through a cloud service with tested conditional writes; a locked desktop's vault file lags behind until it is unlocked ([ADR-0013](decisions/0013-device-sync.md)).
